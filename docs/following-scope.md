# Following & friends — scope

Status: **tabled 2026-09-26.** Scoped, nothing built; the five questions below are still open. Stage 4 went to polishing saves, notifications and reactions instead.

## Where the product stands

Access today is **the link, not a relationship**. Every container — vault, collection, fit, piece — is `private` or `link_only`, reached by an unguessable token. Saving (Stage 2) is the only thing that needs an account, and notifications fan out from saves: you hear about a container because you kept its link.

That model was deliberate (`fit_reactions.sql`: "Access is the token, not a follow"). A follow graph changes it: for the first time, *who you are* decides what you see, not *what you were sent*. Everything below follows from that.

Already in place and reusable:

- `container_visibility` enum has an unused third value, **`invite_only`**, which was reserved for exactly this.
- `saves` + `notifications` (kinds `addition`, `reaction`, `save`), coalesced per container per three hours, generated by triggers.
- `pieces.is_private` hides a piece from every container view.
- `piece_private` keeps owner-only data (price paid, estimated value) off every shared read.

## The decision that shapes everything: follow or friend?

| | **Follow** (one-way, Instagram) | **Friend** (mutual, request + accept) |
|---|---|---|
| Fits a personal archive | Collectors you admire, strangers | People you actually know |
| Privacy default | Needs public-ish profiles to mean anything | Works with everything private by default |
| Moderation load | Higher — anyone can attach to you | Lower — you approve each one |
| Discovery | Drives growth | Grows slowly |

**Recommendation: friends first (mutual, request-based), with follow possible later.** The archive is personal and currently private by default; a mutual model adds an audience without asking anyone to go public. A one-way follow can be layered on later as "public profiles", which is a separate decision.

## Proposed v1

1. **Friend requests.** Send from a shared vault/fit page or by username search; accept / decline / remove. No friend counts shown publicly.
2. **A third visibility: "friends".** Use the reserved `invite_only` value, labelled "friends" in the UI, on vault, collection and fit. `is_private` pieces stay hidden from friends too.
3. **Friends see what's shared with friends** through the same security-definer reads the link model uses (`shared_vault`, etc.), gated by friendship instead of — or as well as — a token.
4. **Activity, not a feed.** A friend logging a fit or adding pieces lands in the existing inbox as a new `kind`. No algorithmic feed in v1.
5. **Estimated value and price paid never cross**, same as today.

## Out of scope for v1

Public profiles / one-way follow · a home feed · comments (reactions already exist on fits) · friend suggestions / contacts import · blocking beyond "remove friend" (needed before any public surface).

## Rough data shape

```text
friendships
  requester_id  uuid → users
  addressee_id  uuid → users
  status        'pending' | 'accepted'
  created_at, accepted_at
  unique (least(a,b), greatest(a,b))   -- one row per pair

is_friend(a, b) → boolean              -- security definer, used by the reads
notifications.kind += 'friend_request', 'friend_accepted', 'friend_activity'
```

Reads: extend `shared_vault` / `shared_collection` / `shared_fit` (or add `friend_vault(username)` etc.) so `visibility = 'invite_only'` resolves when `is_friend(auth.uid(), owner)`. RLS on `friendships`: each side sees only rows they are part of.

## Questions for you

1. **Friends (mutual) or follow (one-way) for v1?** Recommendation above is friends.
2. **Default visibility for friends:** does accepting a friend show them anything automatically, or only containers you explicitly set to "friends"? (Recommendation: explicit — nothing changes until you choose.)
3. **How do people find each other:** username search only, or also from a shared link ("add @dillon as a friend")?
4. **Activity:** should friends' new fits/pieces notify you, or only show up when you visit them?
5. **Web too, or app-first?** The shared web pages would need the "add friend" entry point either way.

## Rough size

One migration (table, function, RLS, reads, notification kinds) · app: friends list, requests inbox section, visibility option, add-friend entry points · web: add-friend on shared pages, "friends" visibility. Comparable to Stage 2.
